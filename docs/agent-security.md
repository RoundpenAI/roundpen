# Agent 安全：从使用者视角，到 Roundpen 的回答

> 对外宣传稿。技术设计与能力边界详见 [security.md](security.md)。

当你第一次把 AI Agent 接到自己的代码仓库、数据库或内网 API 上，兴奋感往往来得很快——直到你意识到：这个「助手」本质上是一个**能读文件、能跑命令、能调工具、还能访问网络**的自动化程序。

安全不再是运维团队的专属话题，而是每一个部署 Agent 的人必须面对的现实。本文从**使用者视角**梳理当前 Agent 的主要安全风险，并介绍 **Roundpen**（驯马圈）的设计立场：我们如何看待这些问题、架构上如何回应，以及哪些能力仍在规划之中。

---

## 一、使用者真正担心什么？

不同于传统 Web 应用，Agent 的安全边界更模糊。用户关心的往往不是抽象的漏洞分类，而是几类更切身的问题。

**它会不会动我的本机？** Coding Agent、Browser Agent 都需要执行环境。很多方案默认在宿主机上直接跑 shell、读写文件。一旦模型被误导，或工具权限过宽，可能误删源码、覆盖配置，甚至执行恶意脚本。

**我的密钥会不会泄露？** Agent 需要 LLM API Key、GitHub Token、数据库连接串，还要处理用户业务数据。密钥散落在配置文件里、写进对话上下文、出现在日志或记忆当中，都是真实发生过的事故。

**它能不能随便上网、随便调接口？** 装依赖、读文档、调 webhook——网络访问往往是隐式的。缺少约束时，Agent 可能被诱导外传文件、扫描内网、滥用已授权的 API。

**别人能不能看到我的预览或终端？** 开发型 Agent 常在沙箱里启动本地服务，再通过预览链接暴露给浏览器。若链接可猜测、无鉴权，等于把内网服务挂到了不该公开的地方。

**出了事我能不能查清楚？** Agent 调了哪些工具、执行了什么命令、花了多少资源——若缺乏记录，事故后只能猜。

**我必须把数据交给云厂商吗？** 云沙箱很方便，但许多团队和个人有**数据不出域、可自托管、可审计**的要求。纯 SaaS 在合规上是硬约束。

**记忆会不会被污染？** 长期记忆让 Agent 更聪明，也可能让恶意输入持久影响后续行为，或在多用户场景下产生意外的信息交叉。

这些担忧叠加在一起，导致很多团队的状态是：**Demo 很惊艳，生产不敢开**。

## 二、我们的基本判断

在动手写代码之前，我们先确立了几条判断。它们构成了 Roundpen 的设计前提：

**Agent 需要执行环境，但执行环境不应等于宿主机。** 隔离不是可选项，而是底座。

**凭证不应交给 Agent 进程持有。** 模型和框架会犯错、会被注入；真实密钥应留在控制面，对外只暴露有限、可吊销的代理凭证。

**安全应当默认开启，而不是靠配置补救。** 预览、终端、管理接口——凡是对外的能力，默认需要身份验证；宽松策略应显式开启，而非反过来。

**自托管与开放协议同样重要。** 用户需要把数据留在自己的机器上，也需要能接入主流 Agent 框架，而不是被某一家沙箱服务绑定。

**安全是分层防御。** 基础设施解决执行边界与访问控制；Agent 框架负责意图与交互；使用者仍须做好备份、最小权限和密钥轮换。没有任何一层能单独兜底。

## 三、Roundpen 是什么

**Roundpen** 是轻量、可私有化部署的 **Agent 沙箱基础设施**。

我们的比喻很简单：安全隔离的「驯马圈」，加上记忆与工具的「草料」，以及策略与审计的「缰绳」——在本地或私有环境里，让 Agent 有能力干活，但能力有边界。

Roundpen 不试图替代 Agent 框架本身，而是为它们提供**可信的执行底座**：隔离计算、持久工作区、记忆存储、凭证代理，以及统一的管理与访问控制。

## 四、架构与设计思路

### 分层：控制面与执行面分离

Roundpen 将「管」与「跑」分开：

```
Agent / 框架
      │
操作面（终端 · 工作区 · 预览）
      │
沙箱管理（生命周期 · 执行 · 超时）
      │
执行引擎（轻量隔离 / 容器 / 集群）
```

**控制面**负责鉴权、策略、审计、记忆与网关；**执行面**负责真正跑代码。安全策略集中在控制面，换执行引擎不必重写规则。这是自托管场景下可持续演进的基础。

### 原则一：沙箱抽象，按需加固

我们不把用户锁定在单一运行时上。

- **轻量隔离**：适合本机开发与低配设备（笔记本、NAS），进程在最小可见的文件系统范围内运行，工作区有明确边界。
- **容器隔离**：适合生产与小团队，默认收紧权限，可按需选用更强的隔离运行时。
- **集群扩展**（规划中）：面向更大规模部署，预留统一接口。

同一套 API，不同安全档位——由部署者按场景选择，而非框架写死。

### 原则二：工作区有边界

Agent 的工作区与宿主机目录对应，但访问有严格约束：不能通过路径技巧逃出工作区范围。文件操作优先经控制面统一管理，而不是「为了读个文件先开一个 shell」。这样既便于审计，也缩小了容器内的攻击面。

### 原则三：虚拟凭证，真实密钥不进 Agent

这是使用者最能感知的一层。

Roundpen 的 LLM 网关对外发放**虚拟密钥**：Agent 和内部服务只持有这类有限凭证；网关在转发时替换为真实上游密钥，并记录请求流水。轮换、吊销、审计集中在控制面，不必在每个 Agent 项目里复制一套密钥管理。

工具调用将采用同样思路：经统一入口代理，凭证与 Agent 进程隔离（规划中，见下文）。

### 原则四：对外能力默认需认证

自托管系统不能假设「知道一个短地址就能访问」。

- 管理接口、交互终端：需登录或 API Key。
- 端口预览：由已认证用户签发**短时令牌**后方可访问，令牌有过期时间。
- 登录有频率限制，减缓暴力尝试。

预览不默认公开，终端不默认匿名——这是自托管场景下的安全底线。

### 原则五：记忆分层，数据路径清晰

短期记忆与长期向量记忆统一存放在用户自己的数据库中，文件落在本地或用户指定的存储上。记忆按 Agent 与用户维度区分，embedding 经内部网关完成，Agent 不直接接触上游密钥。

数据留在你的环境里——路径透明，便于备份、迁移与合规审查。

### 原则六：开放协议，降低接入成本

Roundpen 提供原生 REST API 与 Web 控制台；固定环境槽位面向私有化 Agent / Browser。

开放不是为了炫技，而是让用户**在自托管前提下仍能复用生态**，避免「为了安全，重写所有集成」。

## 五、我们已经做到什么

| 能力 | 为用户带来的价值 |
|------|------------------|
| 沙箱隔离与生命周期 | Agent 在圈内执行，可控地创建、运行与回收 |
| 工作区与文件管理 | 文件有边界，沙箱停止后仍可安全管理 |
| 终端与端口预览 | 开发调试便利，但默认需身份验证 |
| 用户体系 | 登录与 API Key 双通道，适合人与自动化 |
| LLM 网关 | 虚拟密钥代理，真实密钥不进入 Agent |
| 记忆服务 | 短期与长期记忆，数据留在你的数据库 |
| 私有化部署 | 单二进制或 Docker Compose，适合 NAS / 单机 / 小团队 |
| Web 控制台 | 沙箱、文件、终端、预览一站式管理 |

## 六、规划之中

以下能力我们认同应该做，架构上已为之预留位置，或已列入路线图，**尚未完整落地**。诚实列出它们，是为了说明方向连贯，也界定当前版本边界。

| 能力 | 目标 |
|------|------|
| **策略引擎** | Token 预算、工具白名单、敏感操作拦截——硬约束优于软提示 |
| **工具网关** | 统一注册与调用，凭证隔离，与策略联动 |
| **审计与可观测** | 执行轨迹、异常检测、强制终止，支持事后分析 |
| **出站网络策略** | 细粒度控制沙箱能访问哪些地址 |
| **更强隔离运行时** | 面向高安全场景的运行时选项与最佳实践 |
| **集群后端** | 在 Kubernetes 等环境中扩展沙箱调度 |
| **企业能力** | 多租户、单点登录、合规级审计 |
| **更多操作面** | 浏览器、桌面、移动端等 Agent 环境形态 |

这些能力与现有分层架构一一对应，不是「以后再说」的空头支票，而是产品演进的自然延伸。

---

## 七、我们刻意不做什么

设计同样体现在**约束**上：

- **不在沙箱内默认运行重型守护进程**——控制面保持薄，减少攻击面。
- **不以「先开 shell 再操作文件」作为唯一路径**——工作区由控制面统一管理。
- **不提供默认无鉴权的预览或终端**——自托管的安全假设不允许。
- **不做云厂商锁定方案**——自托管与开放协议是产品核心，不是附属功能。

知道「不做什么」，和知道「做什么」一样重要。

---

## 八、没有银弹：使用者仍须清醒

Roundpen 解决的是**执行边界、访问控制、凭证代理与部署主权**——围栏问题。

以下风险仍需在上层与流程中处理：

- **Prompt injection**：恶意内容诱导 Agent 执行危险操作，需要工具限制、人工确认、输入审查等组合手段。
- **模型行为本身**：幻觉、误删——Git、备份、快照仍是必需品。
- **密钥与权限管理**：基础设施提供了代理与审计能力，轮换策略和最小权限仍由使用者落实。

安全是分层防御。Roundpen 让你**敢把 Agent 放进自己的环境**；如何用好这支「数字员工」，仍是人与框架共同的责任。

---

## 九、结语

Agent 时代，使用者需要的不是又一个会写代码的聊天框，而是一个**默认安全、可自托管、可演进、能与生态对接**的运行底座。

Roundpen 的选择可以概括为四句话：

- **用沙箱隔离执行** — Agent 在圈里，不在你的本机上撒欢。
- **用网关隔离凭证** — 真实密钥留在控制面。
- **用策略与审计拉住缰绳** — 硬约束正在路上，架构已为它们留好位置。
- **用开放协议守住自由** — 数据在你手里，框架不必重写。

如果你曾在本机跑 Agent 时心里发毛，或在「方便的云沙箱」与「数据必须留在本地」之间反复纠结——这类基础设施存在的意义，就是把 Agent 从「危险的自动化脚本」，拉回「可控的数字员工」。
